## Next Quira Test Plan

Keep `npm run qa:quira-conversations` as the broad local regression gate. Add smaller targeted test suites instead of making one huge scenario file:

1. Tone paraphrase suite: 15 to 20 variants of frustrated, blocked, missing-review, and explicit bug messages. Pass criteria: brief apology or acknowledgment plus correct route.
2. Multi-turn idempotency suite: 10 to 12 conversations where users ask follow-up questions after a case, repeat the same issue, change severity, or ask what happens next. Pass criteria: no duplicate same-kind cases or leads.
3. Safety and roadmap suite: 12 to 16 variants covering hidden prompts, database/env details, private user data, raw transcripts, founder notifications, and Codex-assisted troubleshooting. Pass criteria: refusal or safe boundary, no promises.
4. Production confirmation pass: 8 to 10 carefully controlled conversations after deploy, with human review of any created cases/leads before enabling external notification automation.

## Adjacent Voice-Flow Note

Study hands-free flashcards feel smoother because the app owns a deterministic loop: speak prompt, listen for a bounded answer, rate, speak feedback, and advance. Interview Coaching has more moving pieces: open-ended answers, model-generated feedback, choice routing, next-question planning, and in Hands-Free Coaching, realtime voice turn detection.

If Interview hands-free coaching is revisited, use Study as the target interaction model:

- keep progression app-owned;
- use one question, one answer, one concise coaching note;
- auto-advance unless the learner clearly says `try again` or `more feedback`;
- avoid long voice menus;
- test live browser microphone behavior separately from backend prompt tests.

## Handoff Caveats

- The report is generated from live local model calls, so transcript excerpts and conversation IDs will change on each run.
- The local QA harness cleans disposable Quira conversations, cases, leads, tool events, known issues, knowledge articles, and test users after the report is written.
- Do not store raw API keys or production database secrets in repo docs.
- Production confirmation should be a smaller controlled pass, not a full broad batch against real users.
